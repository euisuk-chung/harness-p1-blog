# 선택 실습: 인계 기록과 증거를 어디까지 믿을 수 있습니까?

이 실습은 선택입니다. 기존 실습의 진행과 판정에 영향을 주지 않으며, 모델이나 API를 부르지 않습니다. 프로그램은 Python 표준 라이브러리로 모의 기록을 읽고 비교만 합니다.

**이 폴더의 모든 자료는 이 과정에서 직접 만든 설명용 예시입니다.** 실제 모델 답변, 발송 기록, 성능 측정 결과가 아닙니다. 각 실행의 첫 줄에도 `MOCK ONLY`가 표시되며, 가상 수치를 실제 업무 성과로 인용해서는 안 됩니다.

## 사본에서 무엇을 확인합니까?

인계받은 담당자는 적힌 내용을 바로 실행하기 전에 현재 업무와 같은 기록인지 확인합니다. 여기서는 요청을 새로 열거나 이전 세션을 재개하지 않고, 인계 기록을 받아들일 조건만 살펴봅니다. 꾸러미 맨 위 폴더(`blog`와 `.venv`가 나란히 있는 곳)에서 다음 명령으로 새 사본을 만든 뒤, 사본의 `blog` 폴더에서 실습합니다.

```bash
LAB_DIR="$(mktemp -d)"
cp -R blog "$LAB_DIR/blog"
cd "$LAB_DIR/blog"
```

이미 꾸러미를 준비하며 설치한 Python과 uv를 사용합니다. 아래 명령의 `--no-project --offline`은 이 실습을 위해 패키지를 추가로 내려받지 않게 합니다.

## 인계 기록은 언제 멈춰야 합니까?

인계 기록 네 건은 같은 요청과 같은 자료를 가리킵니다. 다만 오래된 기록은 시각이 다르고, 파일이 빠진 기록은 실제로 없는 초안 파일을 가리키며, 다른 코드로 만든 기록은 코드 확인값이 다릅니다. 확인값은 글자 하나가 바뀌어도 달라지는 SHA-256 값이며, 프로그램은 현재 원문과 코드 문자열을 UTF-8로 읽고 인계 파일의 실제 바이트도 읽어 확인값을 매번 다시 계산합니다. 인계 파일은 이 실습 폴더 안의 상대 경로로만 읽습니다.

비교 기준은 `cases.json`의 `current`에 고정돼 있습니다. 현재 시각은 파일 속 UTC 시각을 사용하므로 실제 실행 날짜가 바뀌어도 같은 결과가 나옵니다. 허용 기간 24시간도 이 예시가 정한 조건이며, 모든 업무에 적용할 권장값은 아닙니다. 코드 문자열은 비교 원리를 보여 주는 작은 함수로, 실제 블로그 프로그램 전체의 버전을 대신하지 않습니다.

먼저 기록 네 건을 한 번에 비교합니다.

```bash
uv run --no-project --offline python labs/evidence/lab.py handoff
```

화면에는 각 기록의 판단, 이유, 저장된 확인값과 다시 계산한 확인값이 나옵니다. 아래는 실행 결과에서 판단과 이유만 추린 내용입니다.

| 기록 | 판단 | 이유 |
|---|---|---|
| `normal` | `REVIEW_ONLY` | 필수 정보·요청·다음 단계·시각·세 확인값이 비교 조건과 일치합니다 |
| `stale` | `STOP` | 기록 시각 허용 범위 밖 |
| `missing` | `STOP` | 인계 파일 없음: artifacts/absent-draft.json |
| `wrong-code-version` | `STOP` | code_sha256 불일치 |

끝날 때 남기는 신호는 **3**입니다. 이는 중단할 기록이 있다는 뜻이며, 예상한 결과입니다. `REVIEW_ONLY`도 글의 발행 허가를 뜻하지 않고, 현재 자료로 검수를 진행할 수 있다는 뜻입니다. 이 실습 프로그램은 검수나 발행을 실행하지 않습니다.

정상 기록 하나만 비교하면 신호 **0**으로 끝납니다.

```bash
uv run --no-project --offline python labs/evidence/lab.py handoff --case normal
```

실제 업무에서는 중단 이유를 없애려고 예전 기록의 시각이나 확인값을 바꿔 적으면 안 됩니다. 담당자가 원자료와 실행한 코드, 진행 상태를 확인한 뒤 새 인계 기록을 남기며, 확인하지 못한 상태에서는 작업을 이어 가지 않습니다.

- **오래된 기록:** 그동안 자료나 진행 상태가 바뀌었는지 다시 확인한 뒤 현재 상태로 인계합니다
- **인계 파일이 없는 기록:** 담당자에게 해당 파일의 보관 위치와 내용을 확인하며, 파일을 찾지 못하면 작업을 이어 가지 않습니다. 파일을 되찾은 뒤에는 실제 내용과 확인값을 다시 대조합니다
- **코드 확인값이 다른 기록:** 어느 코드로 처리했는지 확인하고, 현재 코드에서 기존 상태를 이어 써도 되는지 검토한 뒤 필요한 검수를 다시 합니다
- **요청·다음 단계·시각이 맞지 않는 기록:** 다른 업무의 기록이나 미래 시각을 그대로 받아들이지 않고 원인을 확인합니다

확인값이 같아도 자료의 내용이 사실인지, 인계자가 권한을 가졌는지, 코드가 안전한지는 알 수 없습니다. 이 프로그램은 고정된 비교 조건만 확인하므로 실제 업무의 인계 장치로 그대로 사용하지 않습니다.

## 통과 문구와 성능 숫자는 무엇을 입증합니까?

모의 기록에는 `pass`라는 문구, 시험용 전송 기록, 실제 전송이라고 적힌 기록, 성능 숫자 두 벌이 있습니다. 문구를 읽기 전에 무엇을 직접 대조할 수 있는지 생각해 보십시오. 다음 명령은 인용문을 원문과 대조하고, 가상 표본이 있을 때만 산술값을 계산합니다.

```bash
uv run --no-project --offline python labs/evidence/lab.py evidence
```

실행 결과에서 다음 질문의 근거를 찾아 답하십시오. 답을 확인할 때는 표시된 문구와 직접 확인한 내용을 나눠 설명합니다.

| 질문 | 실행 결과에서 확인할 근거 | 여기까지 말할 수 있습니다 |
|---|---|---|
| `pass`면 인용도 맞습니까? | `status_label`은 `pass`지만 `quote_found_in_source`는 `false`입니다 | 원문에는 2건, 인용문에는 3건이 적혀 있어 그대로 인용하지 않았습니다 |
| 시험용 성공은 실제 전달 증거입니까? | `test-only`의 전송 방식은 `fake`이고 수신 기록은 `null`입니다 | 시험용 기록에서 응답 숫자를 확인했으며 실제 수신은 확인하지 못했습니다 |
| `live`라고 쓰면 실제 전달이 확인됩니까? | `live-claim`에는 `http`와 202가 있지만 수신 기록은 `null`입니다 | 실제 서비스의 접수·처리·수신 근거가 더 필요하며, 이 자료 자체도 모두 모의 기록입니다 |
| 고정된 40%는 계산으로 확인됩니까? | `hardcoded`의 표본 수는 0이며 계산값은 `null`입니다 | 비교할 표본이 없어 40%의 근거를 이 파일에서 확인할 수 없습니다 |
| 가상 표본은 40%와 맞습니까? | `synthetic-samples`는 두 쌍에서 9.09%를 계산합니다 | 가상 표본의 평균 변화는 9.09%이며, 이 계산도 실제 성능 향상을 입증하지 않습니다 |

가상 표본의 앞선 값은 100·120ms, 뒤의 값은 90·110ms이므로 평균은 110ms에서 100ms로 줄어듭니다. 프로그램은 `(이전 평균 - 이후 평균) / 이전 평균 × 100`을 계산하며, 비어 있거나 개수가 다르거나 양수가 아닌 표본은 계산하지 않습니다. 파일에 적힌 40%는 이 계산에 쓰이지 않습니다.

이 명령의 신호 **0**은 기록을 읽고 계산을 마쳤다는 뜻입니다. 모든 주장에 근거가 있거나 실제 업무가 성공했다는 뜻으로 읽지 마십시오. 실제 효과를 판단하려면 같은 조건에서 수집한 원자료, 비교 방식, 반복 측정, 실패 사례까지 확인해야 합니다.

## 승인 전에 지금 파일의 근거를 어떻게 읽습니까?

이 부분은 **11차시 판정을 마친 뒤**에 하는 선택 실습입니다. 5차시의 강화 형식과 9차시의 검사 다섯이 준비된 꾸러미를 사용하며, 아직 그 단계 전이면 이 부분은 나중에 읽습니다. 앞에서는 직접 만든 모의 기록을 읽었지만, 여기서는 꾸러미에 저장된 초안을 현재 규칙으로 실제로 다시 검사합니다. 검사에 쓰는 원문은 설명용 합성 자료이므로, 실제 모델이나 논문에 관한 사실을 검증하는 실습은 아닙니다. 새 모델 호출이나 외부 발송 없이 승인에 필요한 근거를 읽습니다.

원래 꾸러미 맨 위 폴더(`blog`와 `.venv`가 나란히 있는 곳)로 이동한 뒤 새 사본을 만드십시오. 첫 줄은 꾸러미를 준비하며 설치한 가상환경을 지정하므로, 사본에서도 기존 검사에 필요한 라이브러리를 그대로 사용합니다.

```bash
export VIRTUAL_ENV="$(cd .venv && pwd)"
APPROVAL_LAB="$(mktemp -d)"
cp -R blog "$APPROVAL_LAB/blog"
cd "$APPROVAL_LAB/blog"
```

사본에 연습용 요청 폴더를 만들고 저장된 초안을 옮깁니다. 외부 PR을 만들지 않도록 환경 변수도 명시적으로 0으로 지정합니다.

```bash
mkdir -p requests
cp -R reference/11-approval requests/evidence-approval
export HACKERS_PR=0
```

다음 명령은 초안을 글로 만든 뒤 검사 근거를 요청 폴더에 남깁니다. 검사 자체는 현재 입력과 코드의 임시 사본에서 실행하므로 원래 요청의 `review.json`은 덮어쓰지 않습니다.

```bash
uv run python scripts/request_approval.py evidence-approval
```

명령은 신호 **3**으로 끝나며 사람이 승인할 차례라는 뜻입니다. 근거는 요청 폴더의 `approval-evidence.md`와 `approval-evidence.json`에 저장됩니다. 먼저 사람이 읽는 카드를 엽니다.

```bash
cat requests/evidence-approval/approval-evidence.md
```

정상 초안으로 확인한 카드에는 아래 내용이 나옵니다. 카드 속 검사 신호 **0**과 승인 명령의 신호 **3**은 서로 다른 일을 말합니다.

- **기대와 관찰:** 기대는 G1~G5 모두 pass와 신호 0이며, 관찰에도 `일치: G1~G5 모두 pass, 신호 0`이 나옵니다
- **검사 코드:** 커밋과 커밋 뒤 변경 여부를 따로 적습니다. 이처럼 Git 기록 없이 복사한 폴더에서는 둘 다 `미확인`일 수 있으므로, 임의의 커밋 값을 채우지 않습니다
- **입력과 글:** 초안과 글의 SHA-256, 검사에 사용한 원문·코드 파일의 확인값을 남깁니다. 파일 내용이 바뀌면 확인값도 달라집니다
- **확인하지 못한 것:** 주장의 사실성·최신성, 인용의 의미, 새 모델 출력, 실제 발행과 외부 서비스는 이번 검사로 확인하지 못했습니다

이제 사본에서 첫 번째 인용문만 원문에 없는 말로 바꿉니다. 원문이나 저장된 검수 결과는 그대로 두므로, 예전의 통과 기록을 새 근거로 읽는지 확인할 수 있습니다.

```bash
uv run python - <<'PYTHON'
import json
from pathlib import Path
path = Path('requests/evidence-approval/draft.json')
draft = json.loads(path.read_text(encoding='utf-8'))
draft['claims'][0]['quote'] = '원문에 없는 인용입니다.'
path.write_text(json.dumps(draft, ensure_ascii=False, indent=2) + '\n', encoding='utf-8')
PYTHON
```

같은 승인 명령을 다시 실행한 뒤 카드를 읽습니다.

```bash
uv run python scripts/request_approval.py evidence-approval
cat requests/evidence-approval/approval-evidence.md
```

이번에도 승인 명령의 신호는 **3**이지만, 카드의 관찰은 `불일치: 규칙 검사 거부`로 바뀝니다. 카드 속 검사 신호는 **1**이고 G3는 `rejected`이며, 입력과 글의 확인값도 달라집니다. 카드가 바뀌어도 원래 요청의 `review.json`은 보존됩니다.

이 상태에서는 승인하지 마십시오. 원문을 확인해 인용문을 고친 뒤 다시 검사해야 합니다. 실습을 처음 상태로 되돌리려면 사본의 초안만 저장된 정상 초안으로 복구하고, 같은 승인 명령으로 새 카드를 만듭니다.

```bash
cp reference/11-approval/draft.json requests/evidence-approval/draft.json
uv run python scripts/request_approval.py evidence-approval
```

복구 뒤에는 관찰이 다시 일치하고 G1~G5가 pass가 됩니다. 그래도 승인 명령은 신호 **3**으로 끝납니다. 이 카드는 사람이 판단할 근거를 덧붙이며, 새로운 차단 장치나 자동 승인 기능을 추가하지 않습니다. 실제 PR 생성·발행·수신은 이 실습의 확인 범위 밖입니다.

## 무엇을 내 업무에 가져갑니까?

다음 담당자가 이어 할 일만 적으면 기록이 어느 상황에 맞는지 빠질 수 있습니다. 원문과 코드의 확인값, 요청과 진행 단계, 작성 시각을 함께 남기되, 일치했다는 이유만으로 검수나 승인을 생략하지 않습니다. 결과를 보고할 때도 상태 문구, 직접 검사한 내용, 실제 운영 증거, 아직 모르는 점을 구분해서 적습니다.
